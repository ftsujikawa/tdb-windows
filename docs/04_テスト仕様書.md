# tdb-windows テスト仕様書

## 1. 目的

本書は、「01_要件定義書.md」の各要件が実装(「02_基本設計書.md」「03_詳細処理設計書.md」)に正しく反映されていることを検証するためのテストケースを定義する。

## 2. テスト方針

- 本ソフトウェアは対話的 REPL であるため、原則として「標準入力へのコマンド列の投入 → 標準出力の内容確認」によるブラックボックステストとする。
- テスト対象実行ファイル(デバッギー)は `examples/` 配下のサンプル(`testprog.c` 等)、または各テストケース専用に用意する C ソースをビルドして使用する。
- 1 テストケースにつき、独立した tdb-windows プロセスを 1 回起動して実施することを基本とする(状態を持ち越さない)。
- 実行環境依存(シンボル/アドレスの実値、スレッド ID、PID)がある項目は、値そのものではなく「表示形式・相対関係・分岐の正しさ」を判定基準とする。

## 3. テスト環境

| 項目 | 内容 |
|---|---|
| OS | Windows 10/11 x64 |
| ビルド | `cargo build`(デバッグ/リリース双方で実施) |
| コンパイラ(テスト対象生成用) | MSVC (`cl.exe`)、`/Zi` でデバッグ情報 (PDB) を出力 |
| 実行方式 | `tdb-windows.exe <対象.exe> [引数...]` を起動し、標準入力へコマンドを送る |
| 権限 | 通常権限・管理者権限の双方で一部項目(TC-PRIV-*)を実施 |

## 4. テストケース一覧

### 4.1 プロセス制御

| ID | 目的 | 事前条件 | 手順 | 期待結果 |
|---|---|---|---|---|
| TC-PROC-01 | `run` によるプロセス起動 | `testprog.exe` を用意 | `run` を実行 | 「Starting: ...」「Process created: {pid}」「Symbols loaded at 0x...」が表示され、初期ブレーク(`Exception 0x80000003 ...`)で停止する |
| TC-PROC-02 | `continue` による再開・正常終了 | TC-PROC-01 の状態 | `continue` を実行 | プログラムの標準出力が表示され、「Process {pid} exited with code 0」が表示される |
| TC-PROC-03 | 再実行による再起動 | プロセス実行中 | `run` を再度実行 | 既存デバッギーが終了し、新しい PID で再起動される |
| TC-PROC-04 | 未起動時の `continue` | 未起動状態 | `continue` を実行 | 「No process is running. Use 'run' first.」を表示し異常終了しない |
| TC-PROC-05 | 子プロセスの生成・追跡 | 子プロセスを起動する検証用実行ファイル(例: `CreateProcessA` で `cmd.exe /c ping ...` を起動)を用意 | `run` → `continue` | 「Child process created: {pid} (main thread {tid})」が表示される |
| TC-PROC-06 | 孫プロセスの追跡 | TC-PROC-05 と同一(子がさらに孫を生成する構成、例: cmd.exe が ping.exe を起動) | `run` → `continue` を繰り返す | 孫プロセスについても「Child process created: ...」が表示される |
| TC-PROC-07 | 子プロセス終了時のセッション継続 | TC-PROC-05 の状態で子プロセスが終了するまで `continue` | `continue` を繰り返す | 「Process {子pid} exited with code ...」表示後もセッションが継続し、後続コマンドが「No process is running」にならない |
| TC-PROC-08 | ルートプロセス終了時のセッション終了 | TC-PROC-07 に続けルートプロセスも終了させる | `continue` を実行し最後まで進める | 「Process {root pid} exited with code 0」の後、以降のコマンドで「No process is running」等が返り、デバッグ対象なし状態になる |
| TC-PROC-09 | `processes` 一覧(単一プロセス時) | プロセス実行中(子プロセスなし) | `processes` を実行 | ルートプロセス 1 件のみ `(root)` 付きで表示される |
| TC-PROC-10 | `processes` 一覧(子プロセス存在時) | TC-PROC-05 の状態 | `processes` を実行 | ルートに `(root)`、子に `(child)` が付き、両方の PID・メインスレッド ID が表示される |
| TC-PROC-11 | Ctrl+C 転送 | 長時間ループするデバッギーを `continue` 中 | Ctrl+C を送信 | デバッガ自身は終了せず、デバッギーが中断されて `Interrupted (Ctrl+C)` を伴い停止する |
| TC-PROC-12 | `quit` によるプロセス終了 | プロセス実行中 | `quit` を実行 | tdb-windows・デバッギーとも終了する(デバッギーのプロセスが残存しないことをタスク一覧で確認) |

### 4.2 ブレークポイント

| ID | 目的 | 事前条件 | 手順 | 期待結果 |
|---|---|---|---|---|
| TC-BP-01 | シンボル名指定での設置 | プロセス実行中 | `break main` | 「Breakpoint #1 set at 0x... [main+0x.. (file:line)] (pid ...)」が表示される |
| TC-BP-02 | `ファイル:行番号` 指定での設置 | 同上 | `break testprog.c:24` | 該当行のアドレスに設置される |
| TC-BP-03 | 生アドレス指定での設置 | 同上 | `break 0x<有効なコードアドレス>` | 指定アドレスに設置される |
| TC-BP-04 | ヒットと表示 | `break main` 設置済み | `continue` | 「Breakpoint hit at 0x... [main+...]」表示、該当ソース行(`=>` 付き)またはコードが表示される |
| TC-BP-05 | 一覧表示 | ブレークポイント 1 件以上設置済み | `breakpoints` | 番号・アドレス・PID・有効/無効・シンボル情報が表示される |
| TC-BP-06 | 削除 | ブレークポイント設置済み | `delete 1` | 「Deleted breakpoint #1 ...」が表示され、以後ヒットしない |
| TC-BP-07 | 存在しない番号の削除 | 未設置状態 | `delete 99` | エラーとなり異常終了しない |
| TC-BP-08 | 未起動時の `break` | プロセス未起動 | `break main` | 「No process is running. Use 'run' first.」を表示 |
| TC-BP-09 | 子プロセスへの生アドレスブレークポイント | 子プロセス生成済み、`thread <子のtid>` 実行後 | `break 0x<子プロセス内の有効アドレス>` → `continue` | 子プロセスの PID で設置され、ヒット時に停止する |
| TC-BP-10 | 異なるプロセスでの同一アドレス非干渉 | ルート・子で偶然同じアドレス値が有効なコードである状況(または人為的に同アドレスへ双方設置) | 双方に同アドレスで `break` | それぞれ独立した番号・PID で管理され、一方の削除が他方に影響しない |

### 4.3 ウォッチポイント

| ID | 目的 | 事前条件 | 手順 | 期待結果 |
|---|---|---|---|---|
| TC-WP-01 | 書き込みウォッチポイント設置とヒット | `testthreads.exe` を `run` 直後(初期ブレークで停止中) | `watch g_shared_counter` → `continue` | 設置成功メッセージの後、書き込み発生時に「Watchpoint #1 hit: g_shared_counter」「Old value = .. / New value = ..」を表示して停止する |
| TC-WP-02 | 複数スレッドからのヒット | TC-WP-01 の状態で複数回 `continue` | `continue` を繰り返す | どのワーカースレッドが書き込んでも検出され停止する(スレッド間で watchpoint が同期されていること) |
| TC-WP-03 | アクセス(読み書き)ウォッチポイント | 同上 | `awatch <変数>` | 読み出し発生時にもヒットする |
| TC-WP-04 | 5 件目設置時のエラー | ウォッチポイント 4 件設置済み | 5 件目を `watch` | 「Cannot set watchpoint: all 4 hardware watchpoint slots are already in use.」を表示し、設置されない |
| TC-WP-05 | サイズ超過時のエラー | 9 バイト以上の構造体等 | `watch <大きな変数>` | 「too large for a hardware watchpoint」を表示し設置されない |
| TC-WP-06 | 一覧表示 | ウォッチポイント設置済み | `watchpoints` | 番号・アドレス・PID・サイズ・種別・式が表示される |
| TC-WP-07 | 削除 | ウォッチポイント設置済み | `deletewatch 1` | 削除メッセージが表示され、以後ヒットしない |
| TC-WP-08 | 別プロセスへの非影響 | 子プロセスを持つ構成でルートにのみウォッチポイント設置 | 子プロセスのスレッドを `continue` で多数実行 | 子プロセス側のスレッドはウォッチポイントの影響を受けない(誤ヒットしない) |

### 4.4 ステップ実行

| ID | 目的 | 事前条件 | 手順 | 期待結果 |
|---|---|---|---|---|
| TC-STEP-01 | ステップイン | `break main` ヒット後 | `step` | 1 命令(または 1 ソース行分)進み、「Step at 0x...」で停止する |
| TC-STEP-02 | ステップオーバー(CALL をまたぐ) | 呼び出し文の直前で停止中 | `next` | 呼び出し先には入らず、呼び出し文の次で停止する |

### 4.5 スレッド管理

| ID | 目的 | 事前条件 | 手順 | 期待結果 |
|---|---|---|---|---|
| TC-TH-01 | スレッド一覧(単一プロセス、複数スレッド) | `testthreads.exe` 実行中、ワーカースレッド生成後 | `threads` | メインスレッドに `(main)`、カレントに `*` が付き、全スレッドが所属 PID 付きで表示される |
| TC-TH-02 | スレッド一覧(複数プロセス) | 子プロセス生成済み | `threads` | ルート・子双方のスレッドが所属 PID 付きで表示される |
| TC-TH-03 | カレントスレッド切替 | 複数スレッド存在 | `thread <他のtid>` | 「Switched to thread {id}: 0x...」が表示され、以後の `regs`/`bt` が当該スレッドの情報になる |
| TC-TH-04 | 存在しないスレッド ID | 同上 | `thread 999999` | 「No such thread: 999999」を表示 |
| TC-TH-05 | `lock` によるフリーズ | 複数スレッド存在 | `lock` | 指定(またはカレント)以外のスレッドが停止し、以後の `continue` で指定スレッドのみ進行する |

| TC-TH-07 | ロック中スレッドの終了 | `lock` 実行後、対象スレッドが終了するまで `continue` | `continue` | 「Locked thread ... exited; lock released and other threads unfrozen.」が表示され、他スレッドが再開する |
| TC-TH-08 | アクセス拒否スレッドの許容 | OS 内部の保護されたワーカースレッドが生成される環境 | 通常操作を継続 | 「Warning: could not sync watchpoints to thread ...: Windows API error: ...」等の警告が出ても後続処理が継続する |

| ID | 目的 | 事前条件 | 手順 | 期待結果 |
|---|---|---|---|---|
| TC-PRIV-01 | 管理者権限での `SeDebugPrivilege` 有効化 | 管理者権限で実行 | 任意のデバッグ操作(特に多数のスレッドを生成するプログラム)を実施 | `GetThreadContext`/`SetThreadContext` に起因する `ACCESS_DENIED` 警告が(通常は)発生しない |

## 5. 合否判定基準

- 「期待結果」に記載した文言・分岐・状態遷移が観測されること。
- 想定外のパニック・強制終了・デバッグイベントループのハング(`ContinueDebugEvent` 未到達によるデバッギー無応答)が発生しないこと。
- エラー系ケース(4.9, 4.2 の異常系等)において、REPL プロセス自体が終了しないこと。
