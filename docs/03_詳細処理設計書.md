# tdb-windows 詳細処理設計書

## 1. 目的

本書は「02_基本設計書.md」で示した各モジュールについて、主要な処理の内部アルゴリズム・分岐条件・状態遷移を、実装(`src/*.rs`)に基づいて詳細化する。

## 2. プロセス起動処理(`process::DebuggeeProcess::launch`)

1. コマンドライン文字列を UTF-16 (`Vec<u16>`) に変換する。
2. `CreateProcessW` を以下のフラグで呼び出す。
   - `DEBUG_PROCESS` (0x00000001): ルートプロセスに加え、その子孫プロセスもデバッグイベント対象にする。
   - `CREATE_NEW_PROCESS_GROUP` (0x00000200): デバッギーを独立したコンソールプロセスグループにし、`GenerateConsoleCtrlEvent` がデバッガ自身を巻き込まずデバッギーだけを対象にできるようにする。
3. 生成された `PROCESS_INFORMATION` から PID・プロセスハンドル・メインスレッドハンドル/ID を取得し、`IsWow64Process` で 32/64bit を判定する。
4. Ctrl+C 転送用の静的変数 `DEBUGGEE_PID` にルート PID を保存する。
5. `processes: HashMap<pid, ProcessEntry>` にルートエントリのみを登録した `DebuggeeProcess` を返す。子プロセスは後述のイベント処理で追加登録される。

`Debugger::restart` はこの結果からルートプロセスハンドルを取得し、`SymbolResolver::new` を呼んでシンボル解決器を初期化する。

## 3. デバッグイベントループ(`Debugger::continue_execution`)

### 3.1 ループ全体の構造

```
loop {
    if 割り込み要求あり { デバッギーへ Ctrl+C 転送 }
    event = WaitForDebugEventEx(timeout=100ms)
    if event なし (タイムアウト) { continue }
    last_thread_id = event.dwThreadId
    pid = event.dwProcessId   // このイベントを発生させたプロセス(常に正)
    match event.dwDebugEventCode {
        EXCEPTION_DEBUG_EVENT => { ... 3.2 節 ... }
        CREATE_PROCESS_DEBUG_EVENT => { ... 3.3 節 ... }
        EXIT_PROCESS_DEBUG_EVENT => { ... 3.4 節 ... }
        CREATE_THREAD_DEBUG_EVENT => { ... 3.5 節 ... }
        EXIT_THREAD_DEBUG_EVENT => { ... 3.6 節 ... }
        LOAD_DLL_DEBUG_EVENT => { ... 3.7 節 ... }
        UNLOAD_DLL / OUTPUT_DEBUG_STRING / RIP_EVENT => 無処理
    }
    ContinueDebugEvent(event.dwProcessId, event.dwThreadId, 継続コード)
}
```

REPL に制御を戻す(`return Ok(())`)分岐以外は、上記末尾の `ContinueDebugEvent` を必ず通過する。これを怠ると当該イベントが未応答のままデバッギーが永久に停止するため、個々の分岐内のエラー処理はすべて「警告出力して処理を継続する」形とし、`?` によるエラー伝播でこの呼び出しをスキップしないよう設計している(スレッド生成時のウォッチポイント同期処理などで顕著)。

### 3.2 EXCEPTION_DEBUG_EVENT の分岐

例外コードにより処理を分岐する。

1. **`STATUS_BREAKPOINT` (0x80000003)** — 以下を優先順位順に判定する。
   a. `pending_leak`(リーク検出における確保系関数の戻り先ブレークポイント)のアドレスと一致 → RAX(戻り値ポインタ)を記録し、フックを再設置して継続。
   b. `leak_hooks` に登録されたアドレスと一致 → 対象関数(malloc/calloc/free)の引数を取得し、malloc/calloc の場合は戻り先にブレークポイントを設置(スタック巻き戻しにより特定)、free の場合は直ちに記録から削除。
   c. `finish_bp`(`finish` コマンドで設置した一時ブレークポイント)と一致 → ブレークポイント除去、REPL に「Returned to ...」を表示して停止。
   d. `step_over_bp`(ステップオーバー中に CALL の戻り先へ設置した一時ブレークポイント)と一致 → 除去後、同一ソース行にとどまっていれば再度ステップを仕込んで継続、そうでなければ REPL に停止を報告。
   e. ユーザー設置のブレークポイント(`breakpoints.get_mut(pid, address)`)と一致 → 元のバイトへ復元し、無効化フラグを立て、`RIP` をブレークポイントアドレスへ巻き戻し、1 命令シングルステップを仕込んで継続(次の `SINGLE_STEP` イベントで再設置するため)。
2. **`STATUS_SINGLE_STEP` (0x80000004)** — ハードウェアウォッチポイントも同じ例外コードで通知されるため、DR6 を確認して切り分ける(`take_watchpoint_hits`)。
   a. `pending_leak_rearm`(リークフックの再設置待ち)があれば、フックを再設置して継続。
   b. `pending_breakpoint`(直前でブレークポイントを一時解除しシングルステップさせた対象)があれば、ブレークポイントを再設置。
   c. ウォッチポイントヒットがあれば、`report_watchpoints` で旧値/新値を表示し停止。
   d. ステップ実行中で同一ソース行にとどまっている場合は継続してステップを仕込み直す。
   e. それ以外は「Step at ...」として停止を報告。
3. **`DBG_CONTROL_C`** — Ctrl+C 転送によりデバッギー内に注入されたハンドラスレッドが発生させる例外。発生スレッドの RIP は無意味なため、代わりにルートプロセスのメインスレッド (`proc.root_main_thread_id()`) のコンテキストを取得して停止位置として表示する。
4. **その他の例外** — 「Exception 0x... at 0x...」として表示し停止する(`DBG_EXCEPTION_NOT_HANDLED` で継続させる)。

### 3.3 CREATE_PROCESS_DEBUG_EVENT

1. `pid == root_pid` かどうかで「ルート自身の生成通知」か「子プロセスの生成通知」かを判定する(`DEBUG_PROCESS` フラグにより、ルート自身の起動時にも本イベントが 1 回発生するため)。
2. ルートの場合: 「Process created: {pid}」を表示する。子プロセスの場合: 「Child process created: {pid} (main thread {tid})」を表示し、`DebuggeeProcess::register_process` により当該プロセスのハンドル・メインスレッド情報を登録する(ルート自身は `launch()` で登録済みのため二重登録しない)。
3. `threads` マップにメインスレッドを登録する(`tid -> pid`)。
4. シンボルロード: `is_root` の場合のみ、`event.u.CreateProcessInfo.hFile` から `SymbolResolver::load_module` を呼び出す。子プロセスの場合はシンボルロードを行わない(基本設計書 3.3 節の方針)。
5. `hFile` ハンドルを `CloseHandle` する。

### 3.4 EXIT_PROCESS_DEBUG_EVENT

1. `pid == root_pid` かどうかを判定する。
2. ルートの場合: 終了コードを表示し、`running = false` とした上で `Debugger::shutdown()` を呼び、`return Ok(())` でデバッグループを抜ける(以後 `self.process` は `None` となる)。
3. 子プロセスの場合: 終了コードを表示し、`DebuggeeProcess::remove_process(pid)` でハンドルを解放する。`threads` マップから当該 PID に属する全スレッド ID を抽出し、`threads`/`frozen_threads` から除去する。ロック中のスレッドが当該プロセスに属していた場合は `locked_thread` を解除する(ただし他プロセスの `frozen_threads` は維持する)。本分岐では `return` せず、ループ末尾の `ContinueDebugEvent` まで到達させ、OS がプロセスを回収できるようにする。

### 3.5 CREATE_THREAD_DEBUG_EVENT

1. 「Thread created: {tid}」を表示し、`threads` マップに `tid -> pid` を登録する。
2. `apply_watchpoints_to_thread(pid, tid)` を呼び、当該プロセスに属する現在有効なウォッチポイントのみをこのスレッドのデバッグレジスタに反映する(`WatchpointManager::dr7_and_addrs_for_pid`)。
3. 本処理は `?` を用いず、失敗時は警告表示のみに留める(一部の OS 内部スレッドが `GetThreadContext`/`SetThreadContext` を拒否するため。要件 F-TH-07/NF-05 に対応)。
4. `lock` 中であっても、新規スレッドは自動的にはフリーズ対象へ追加しない(既存スレッドが依存し得る OS/CRT 内部スレッドをデッドロックさせないため)。

### 3.6 EXIT_THREAD_DEBUG_EVENT

1. 「Thread exited: {tid}」を表示し、`threads`/`frozen_threads` から除去する。
2. `locked_thread == Some(tid)` の場合、`frozen_threads` に含まれる全スレッドを `resume_thread` で再開し、`locked_thread` を解除する(ロック対象自体が消えたため)。

### 3.7 LOAD_DLL_DEBUG_EVENT

`pid == root_pid` の場合のみ `SymbolResolver::load_module` を呼び出す。子プロセスの DLL ロードはシンボル解決対象としない。

## 4. ブレークポイント設置/解除処理

### 4.1 アドレス解決(`Debugger::resolve_target_address`)

入力文字列の種別に応じ、`(pid, address)` を返す。

| 入力形式 | 解決方法 | 対象 PID |
|---|---|---|
| `ファイル名:行番号` | `SymbolResolver::resolve_by_file_line` | `root_pid` 固定 |
| `0x...` / 10進数字列 | `commands::parse_address` | `current_pid()`(カレントスレッドが属するプロセス) |
| それ以外(シンボル名) | `SymbolResolver::resolve_function_entry` | `root_pid` 固定 |

シンボル解決を伴う 2 経路が `root_pid` 固定であるのは、`self.symbols` がルートプロセスのモジュール情報のみを保持しているため。

### 4.2 設置(`set_breakpoint`)

1. `resolve_target_address` で `(pid, address)` を得る。
2. `DebuggeeProcess::set_breakpoint(pid, address)`:
   a. 対象アドレスの現在の 1 バイトを `ReadProcessMemory` で退避。
   b. `VirtualProtectEx` でページ属性を `PAGE_EXECUTE_READWRITE` に変更。
   c. `WriteProcessMemory` で当該バイトを `0xCC` (INT3) に書き換え。
   d. ページ属性を元に戻す。
   e. 退避したバイトを返す。
3. `BreakpointManager::add(pid, address, original_byte)` で管理下に置き、採番した ID を返す。

### 4.3 ヒット時の処理

3.2 節 1-e に記載の通り。ヒット後、元のバイトへ復元 → RIP を巻き戻し → 1 命令シングルステップ → 次の SINGLE_STEP イベントで INT3 を再設置、という手順を踏む。これは「ブレークポイント設置アドレスの命令を、無限に INT3 で止まることなく 1 回だけ正しく実行してから再度ブレークポイントとして機能させる」ための標準的な手法である。

### 4.4 削除(`Command::Delete`)

`BreakpointManager::remove_by_id(id)` で `Breakpoint`(`pid` を含む)を取得し、`DebuggeeProcess::remove_breakpoint(pid, address, original_byte)` で退避しておいた元のバイトへ書き戻す(手順は 4.2-2 と同様、書き込む値が異なるのみ)。

## 5. ステップ実行処理

### 5.1 ステップの仕込み(`arm_step`)

1. カレントスレッドの RIP を取得。
2. `current_pid()` の RIP 位置から最大 16 バイトを読み出し、`disasm::decode_one` で 1 命令デコードする。
3. ステップオーバー (`next`) かつデコード結果が CALL 系命令の場合:
   - 命令長から「戻り先アドレス」を算出し、既存ブレークポイントと重複しなければ一時ブレークポイントとして設置(`step_over_bp` に記録)。
4. それ以外(ステップイン、または CALL 以外の命令)の場合:
   - `EFLAGS` の トラップフラグ (TF, 0x100) を立てて 1 命令シングルステップを予約する(`single_step`)。

### 5.2 継続判定(`should_keep_stepping`)

ステップ開始時に記録した (ファイル, 行番号) と、現在の RIP から解決した (ファイル, 行番号) を比較し、一致する間は「同一行内」とみなしてステップを継続する。シンボル/行情報が得られない場合は継続しない(直ちに停止する)。

## 6. ウォッチポイント処理

### 6.1 設置(`set_watchpoint`)

1. 入力式を `eval::parse` でパースする。
2. `make_eval_context()`(カレントスレッドの評価コンテキスト、`pid = current_pid()` を含む)で式のアドレス・サイズ・現在値を評価する。
3. `watchpoint::hw_size` によりサイズを 1/2/4/8 バイトに丸める(不可なら不可の旨をエラー表示)。
4. `WatchpointManager::add(pid, expr, address, size, kind, initial_value)` で空きスロット(0-3)に登録する。空きが無ければ失敗を通知する。
5. `sync_watchpoints_to_threads()` で全スレッドのデバッグレジスタへ反映する。

### 6.2 DR7 エンコード(`WatchpointManager::dr7_and_addrs_for_pid`)

対象 `pid` に一致するスロットのみを対象とし、各スロット `i` について以下を設定する。

- `DR{i}` = 監視アドレス
- `DR7` ビット `2i`(ローカルイネーブル)を 1 に設定
- `DR7` ビット `16+4i` (2bit): 種別(Write=`01`, Access=`11`)
- `DR7` ビット `18+4i` (2bit): サイズ(1B=`00`, 2B=`01`, 8B=`10`, 4B=`11`)

`pid` が一致しないスロットは無効(該当ビットを立てない)として扱う。これにより、あるプロセスのウォッチポイントが別プロセスのスレッドへ誤って適用されることを防ぐ。

### 6.3 ヒット検出(`take_watchpoint_hits`)

1. 有効なウォッチポイントが 1 件も無ければ空を返す。
2. 対象スレッドの DR6 を取得し、下位 4 ビット(各スロットのヒットフラグ)を確認する。
3. ヒットしたスロット番号一覧を `WatchpointManager::slots_hit` で取得する。
4. 当該スレッドが属する `pid` の DR7/DRi を再構成して書き戻す(DR6 のヒットフラグをクリアするため。クリアしないと同じヒットが報告され続ける)。

### 6.4 スレッド生成時の同期

3.5 節の通り、新規スレッド生成時に当該スレッドの所属プロセスのウォッチポイントのみを反映する。デバッグレジスタはスレッドごとに独立しているため、既存スレッドへの反映(6.1-5)だけでは新規スレッドに効果が及ばない。

## 7. マルチプロセス/マルチスレッド管理処理

### 7.1 `current_pid()` の導出

```
current_pid():
    if last_thread_id が threads マップに存在する:
        そのプロセスIDを返す
    else if self.process が Some:
        root_pid を返す
    else:
        0 を返す(呼び出し側で「プロセス未起動」として扱われる)
```

`thread <id>` により `last_thread_id` が更新されると、以後のブレークポイント(生アドレス指定)/メモリダンプ/逆アセンブル/式評価/`list` コマンドの対象プロセスもあわせて切り替わる。

### 7.2 `threads`/`processes` コマンドの表示

- `threads`: `Debugger.threads` の全エントリを (スレッドID, 所属PID) でソートし、各スレッドの `GetThreadContext` を試みて RIP を表示する。カレントスレッドには `*`、各プロセスのメインスレッドには `(main)`、ロック/フリーズ状態には `(locked)`/`(frozen)` を付与する。コンテキスト取得に失敗したスレッド(アクセス拒否等)は `<context unavailable>` と表示し処理を継続する。
- `processes`: `DebuggeeProcess::list_processes()` が返す `(pid, メインスレッドID, is_root)` を PID 順に表示し、ルートには `(root)`、子には `(child)` を付与する。

### 7.3 `lock`/`unlock`

- `lock [id]`: 対象(省略時はカレントスレッド)以外の全既知スレッドを `SuspendThread` で追加サスペンドし、`frozen_threads` に記録する。既にロック中の場合はロック対象の切替(旧対象を新たにフリーズし、新対象を再開)として扱う。
- `unlock`: `frozen_threads` の全スレッドを `ResumeThread` で再開し、状態をクリアする。
- サスペンド/レジューム操作はスレッド単位のベストエフォートとし、一部スレッドで失敗しても他スレッドへの処理は継続する。

## 8. シンボル解決処理(`symbols.rs`)

- `SymbolResolver::new(handle, search_path)`: `SymInitializeW` によりルートプロセスのハンドルに対してシンボルセッションを初期化する。
- `load_module(file_handle, base)`: `SymLoadModuleExW` でモジュール(実行ファイル/DLL)のシンボルをロードする。
- `resolve(address)`: `SymFromAddrW` 等により、アドレスから「関数名+オフセット」および行情報を取得する。
- `resolve_function_entry(name)` / `resolve_by_file_line(file, line)`: シンボル名または `ファイル:行` からアドレスを取得する(`break`/`disassemble`/`list` から利用)。
- `stack_trace` / `unwind_return_address`: `StackWalkEx` 系 API によりコールスタックまたは 1 段分の戻りアドレスを取得する(`backtrace`、`finish`、リーク検出の malloc/calloc 戻り値捕捉で利用)。
- `resolve_variable` / `enum_locals` / `enum_globals`: ローカル変数・引数・グローバル変数の探索(`print`/`show locals|args|globals` から利用)。
- 型情報系 (`type_tag` / `type_pointee` / `type_member` / `type_size` 等): `SymGetTypeInfo` のラッパーで、構造体メンバオフセット・配列要素型・ポインタの指す型などを解決し、`eval.rs` の型付き読み書きおよび `debugger.rs` の整形表示(`format_aggregate` 等)から利用される。

## 9. 式評価処理(`eval.rs`)

### 9.1 構文解析

再帰下降パーサにより、以下の優先順位(低→高)で式を解析する。

```
比較(== !=) > 比較(< > <= >=) > ビットOR(|) > ビットXOR(^) > ビットAND(&)
> シフト(<< >>) > 加減算(+ -) > 乗除余(* / %) > 単項(- + ! ~ * &) > 後置(. -> [])
> 一次式(整数/浮動小数点/識別子/レジスタ/括弧)
```

識別子は変数名、`$` 始まりはレジスタ名として字句解析される。

### 9.2 評価(`eval` / `eval_location`)

- `eval`: 式を再帰的に評価し、`Value`(整数/浮動小数点)を返す。変数・レジスタの実体アクセスは `EvalContext` トレイトを介して行う(`debugger.rs` の `DebugEvalContext` が実装し、対象プロセス `pid` ・カレントスレッドのレジスタコンテキストを保持する)。
- `eval_location`: 代入(`set`)やウォッチポイント設置など「アドレスが必要な」文脈向けに、式が指すメモリ位置またはレジスタ名を `Location` として返す。
- メンバアクセス(`.`/`->`)・配列添字(`[]`)は、`SymbolResolver` の型情報(`shape`/`element`/`member`)を用いてオフセット・要素型を解決する。

## 10. メモリリーク検出処理

### 10.1 開始(`leak start`)

1. ルートプロセスのシンボルから `malloc` / `calloc` / `free` のエントリアドレスを解決する。
2. 各アドレスに `DebuggeeProcess::set_breakpoint(root_pid, addr)` でブレークポイントを設置し、`leak_hooks` に (種別, 退避バイト) を記録する。1 件も解決・設置できない場合は追跡を開始しない。

### 10.2 ヒット時(イベントループ内、3.2-1-b/a 参照)

- `malloc`/`calloc` ヒット時: 引数(`calloc` はサイズ×個数)を記録した上で、スタック巻き戻しにより戻り先アドレスを特定し、一時ブレークポイント (`pending_leak`) を設置。戻り先ヒット時に RAX(確保されたポインタ)を `allocations` マップへ記録する。
- `free` ヒット時: 引数(解放対象ポインタ)を `allocations` から削除する。
- 戻り先が特定できない場合(`free` 含む)は、フック箇所を 1 命令シングルステップさせてから再設置する(`pending_leak_rearm`)。

### 10.3 停止(`leak stop`)

`leak_hooks` に登録された各アドレスについて `DebuggeeProcess::remove_breakpoint(root_pid, addr, original_byte)` を呼び、元のバイトへ復元する。

### 10.4 報告(`leak report`)

`allocations` の内容(アドレス・サイズ)を一覧表示し、合計サイズを算出して表示する。

## 11. SeDebugPrivilege 有効化処理(`process::enable_debug_privilege`)

1. `OpenProcessToken(GetCurrentProcess(), TOKEN_ADJUST_PRIVILEGES | TOKEN_QUERY)` で自プロセスのトークンを取得。
2. `LookupPrivilegeValueW(None, SE_DEBUG_NAME)` で `SeDebugPrivilege` の LUID を取得。
3. `AdjustTokenPrivileges` で当該特権を `SE_PRIVILEGE_ENABLED` として有効化する。
4. いずれかの手順が失敗した場合は、以降の手順を中断してそのまま処理を継続する(戻り値は無く、失敗はすべて無視される)。管理者権限で実行していない場合、トークンに当該特権が含まれずここで失敗するのが通常の挙動であり、この場合は以降デバッグ対象スレッドへのアクセスが一部拒否される可能性があるが、デバッグループ自体は 3.5 節の警告処理により継続する。

## 12. Ctrl+C 転送処理

1. `install_interrupt_handler` で `SetConsoleCtrlHandler` にハンドラを登録する。
2. ハンドラは `CTRL_C_EVENT`/`CTRL_BREAK_EVENT` 受信時、`INTERRUPT_REQUESTED` フラグ(アトミック変数)を立てて `TRUE` を返す(既定動作である自プロセス終了を抑止する)。
3. デバッグイベントループの先頭(3.1 節)で毎回 `take_interrupt_requested()`(フラグを読み取り同時にクリア)を確認し、立っていれば `GenerateConsoleCtrlEvent(CTRL_C_EVENT, root_pid)` によりルートプロセスへ Ctrl+C を転送する。
4. `CREATE_NEW_PROCESS_GROUP` によりルートプロセスは専用のコンソールプロセスグループに属しているため、この転送はデバッガ自身には作用しない。
